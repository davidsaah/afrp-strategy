Breeze parity for the clubs — the crosswalk and the plan

What Breeze does, what the Hub already does, what is built next, and what the Federation sees rolled up

Source: design/AFRP-Breeze-Club-Parity.md in the public repository. The design record outranks this rendering only in the sense that the file is the record (D41); the page is generated from it.

What Breeze does, what the Hub already does, what is built next, and what the Federation sees rolled up

Written 14 September 2026 on David's direction of that day: "we use breezechms.com for managing the clubs. Take a deep dive into what it is able to do and integrate it into the platform where each of the clubs has the same capability as this and the federation has the ability to see the roll up of it." It extends, and does not replace, AFRP-Addendum-2-Breeze-Replacement.md §3 (August 2026), which established that a federation uses roughly 70% of a church management system and that three things are genuinely hard: texting, child check-in, and twenty-six migrations that are each a relationship.

Sources, read 14 September 2026: breezechms.com (home, pricing), the Breeze API reference (app.breezechms.com/api), and the support knowledge base articles Setting Up Check In at Your Church, Follow Ups, Getting Started With People, Getting Started With Users & Roles, How To Use Tags, Volunteer Management — Getting Started, Getting Started with Events, Online Directory with Member Access; GetApp's feature inventory for Tithely Church Management. Breeze is now sold as "Tithely Church Management" at a flat $72 a month with unlimited admin users and people, texting at 250 messages a month then $10 per 500, worship tools as a $29 add-on. The API is key-per-church, read and write, no webhooks, some responses cached up to fifteen minutes, wrappers "not necessarily created or maintained by Breeze".

1. Breeze, as it reads today

Breeze has one object at the centre — the person profile with families, custom profile fields and a status — and everything else hangs off it.

Module What it actually does (support documentation)
People Profiles with configurable fields; families; filters as simple or compound as needed (wildcards, "has any data", "has no data", exact); saved searches; a default filter per user; the Action Panel on any filtered list — email, text, export (Excel, printed/PDF directory, mailing labels, name tags, mail-merge letter), save the search, assign/remove tags in bulk, update a field in bulk, archive, delete.
Tags Folders of tags; a person in any number of tags; bulk assign from a filtered People list; tags drive event eligibility and reporting; a tag has no leader — the guidance is to put the leader's name in the tag's name.
Events Calendars (several, with per-user permission and website publishing), recurring events, external calendar sync; per event: Overview (attendance total, comparison graph), Attenders (attended / eligible-but-absent, filterable), Reports (by date and event, consecutive misses, printable sheets), Check In, Alerts (email when someone has missed N events), Volunteers, Settings.
Check In Eligibility "Everyone" or specific tags; modes incl. self check-in kiosk; name tags with profile fields, allergies, and a 3–4 digit security code shared between child and parent for secure pick-up; a check-out option; attendance is what check-in records.
Volunteers Per event: Teams → Roles with a quantity needed and a leader (notifications sent from the leader); Assign mode (schedule people) or Invite mode (people choose); reminders; declined RSVPs; blockout dates in Member Access.
Follow Ups Options (name, description, default assignee, days to complete) then assignments of an option to a person — from the profile, the Follow Ups menu, in bulk, or to a whole tag; a dashboard of assigned-to-me / all; complete from the email; weekly summary; bulk actions on the people behind a set of follow-ups. The stated purpose: "ensures people don't fall through the cracks, provides team accountability".
Forms Public forms (link, embed) whose entries attach to a profile; field types text/essay/choice/dropdown/date/address/signature; used for registrations.
Giving Online giving by web and by text; recurring; funds; batches of contributions entered by hand; associations of transactions with profiles; giving reports (top givers, year-to-date); statements members can print themselves; pledge campaigns.
Communications Email to any list with a drag-and-drop editor; texting to any list; unsubscribe managed by the member.
Users & Roles Account owner; default roles Admin (everything, incl. finance), Standard (people, tags, events, follow-ups, forms; no finance), Limited (view people), Check In (a volunteer who runs the kiosk and can add a person there), Member (own profile and family, own giving, online giving, the directory tag). Custom roles per area; the guidance is to keep roles broad.
Member Access / Online Directory A tag named "Online Directory" plus a Member-role permission to view people in it; members then see a People section of exactly those; per-field visibility; an opt-out article.
Reports People, contributions and attendance reports from filters, in table and graph form; Excel export.
Move-in / API Excel import of people; the API for people, tags, events, attendance, volunteers, forms, contributions, families, account log.

A second reading, module by module, of about a hundred and ninety support-centre articles (Breeze's own help centre and the Tithely-hosted copies of the same screens), the API reference, the pricing page and the Tithely terms and privacy documents, through the intake process (D54). What it adds to or corrects in §1, and what each point changes in the plan:

Module What the deeper read established What it changes
The product Breeze was folded into "Tithely Church Management" in November 2025; its help centre still stands alone; billing, the terms and the privacy policy are Tithely's (updated September 2026). One flat monthly plan per account, unlimited people and users. Each club's Breeze is its own account, its own contract and its own Account Owner. "A club on Breeze" means a volunteer holds a contractual role the Federation cannot see into.
People No membership object. Status, dues, tenure and club are custom profile fields or tags; there is no state machine and no dates unless a field holds them. Custom fields are nine types; locked default fields; no per-field history. The Action Panel acts on any filtered list (mail, text, export, tag, bulk update, archive, delete). Merge is name-match only and irreversible; delete requires archive first and relabels the person's gifts "Anonymous"; thirty-day recovery. Notes are unsearchable and private notes are exportable by anyone with Export. The extract must read every custom field and classify it (§4.4 of the club plan); a Breeze "Status" value is evidence for a standing proposal, never a standing. Archived people arrive as ended club memberships, not as absences.
Families One family per person; five roles (Head, Spouse, Adult, Child, Unassigned); the household's data is the Head's data; no article describes anything changing at eighteen; a child of two households is a documented workaround. Members cannot add family members without an admin. Breeze's "Child" role is not an age; the register's minor test is the birthdate under R6. A two-household child in Breeze is a case for the merge queue, never an automatic household.
Tags Folders hold tags only; no leader seat (the name carries it); no dates on tag membership in any article read; no duplication; Smart Tags auto-assign from profile-field filters hourly and can lock a tag against hand edits. Tags drive event eligibility, mailing, the directory and role scope. A Smart Tag is a derived list: it imports as the filter that defined it (a note on the group), not as a frozen group. A locked tag that stood for "active members of this club" is standing, already held by the register.
Member Access and the directory A login is given per profile with a role; self sign-up needs an exact name-and-email match; the directory is a tag plus per-field View permissions on the Member role; no native opt-in or opt-out (a Yes/No custom field plus a Smart Tag is the documented workaround); per-item private flags on phones and emails hide them from directories. The directory tag and the opt field are evidence of a display choice; the private flags are evidence of a contact choice per item. Both import as unconfirmed consent proposals (club plan §8.3); the register's three consents are stronger and the member confirms them on first sign-in.
Users and roles Allow/Restrict scoping per role, exclusion wins; finance separation by removing Giving, Users & Roles, Export and Log; only the Account Owner holds the API key, is the contractual contact and can cancel; changing a departed owner needs a signed letter on letterhead. The account log is record-level, in UTC, declared non-exhaustive. Two-factor authentication is not documented. The key for the import comes from a named volunteer, the club's Account Owner; a club whose owner has left must first recover ownership by Breeze's paper process. This goes on the migration's readiness list.
Events Multiple calendars with role-based Allow/Restrict; recurrence weekly, monthly-by-weekday or monthly-by-date only (no "2nd and 4th"); editing a series schedule wipes future check-in and volunteer data; one-way iCal feeds each way; no native registration, RSVP, waitlist or per-option capacity — sign-ups are Forms with a whole-form cap, and eligibility can be "form respondents". Per-recurring-event Alerts email a named person the morning after someone misses a range of consecutive events. B2's events are already stronger (signups, waitlist, questions, recurrence as a series). The extract must take each series' attendance before anyone edits it. The "missed the last N" follow-up is the Hub's answer to Alerts.
Check-in Modes: Search, List, Kiosk (phone number or barcode only, self-service, password-lockable settings); walk-up creates a profile at the door; Check In By Family; Include Checkout records in and out times; Headcount records anonymous attendance; barcodes; thumbnail capture. Name tags on label printers with a 3- or 4-digit code printed on the child's and the parent's tag. No article read describes Breeze checking the code at pick-up; the articles describe a printed match; the check-out report cannot be exported. One check-in list per event. B2's R6 release list is not parity: in the articles read, Breeze's code is a printed convention and no check is described. Gaps worth adding to B2b: a kiosk mode (self check-in by a member's own phone number or QR, which JM-018 already names), check-out times, and an anonymous headcount beside named attendance.
Attendance A by-product of check-in, headcount or import; per-event graphs and table reports; "missed > the last N" filters; twelve saved reports; printable attendance sheets; Excel per event series; the account-level export excludes attendance entirely. Attendance moves only through the API (per event) or per-series reports; the extract step plans for it. Whether a club may print its own event's attendance sheet joins §5 q7.
Volunteers Teams and roles live on an event; quantity and a leader per role; Assign mode (search by name, recent, tag; conflicts flagged; recurrence per person) and Invite mode (sign-up sheets for up to 32 events, personal links only); up to three reminders per role with optional SMS and RSVP; blockout dates set by the volunteer on their own profile. B2b's scope is assign and invite as §3 says, and should add reminders and the volunteer's own blockout dates on the member lens, which the record did not name.
Follow Ups Options (name, description, default assignee, days); assignment singly, in bulk or to a whole tag; completion from the email without login; weekly summary; eight permissions; no bulk complete. B1 has this.
Automations Six account-wide tasks: Smart Tags, a birthday email, Follow Up Progression (complete one, start the next), Follow Up with New Givers, Follow Up with New Attenders, Auto-Tag Form Respondents; a multi-step progression recipe in beta. No article read describes an email on a tag change or a workflow builder. B1's "nothing automatic without a named rule" stands. Two rule-named options worth offering a club beside the lapse rule: a follow-up on a person's first attendance at the club, and on a new club membership. Each a switch the club turns on, each follow-up naming the rule (design choice for C2).
Forms Thirteen field types, file upload, payments to a fund, max entries, confirmation email, custom URL; no signature field, no login, no one-entry-per-person; conditional logic is not documented; entries attach to a profile only on an exact match, otherwise by hand; deleted entries are unrecoverable. Breeze's own article explains how to run elections on a form, with no eligibility check. §5 q6 is largely answered: what clubs build in Breeze forms is event sign-ups, interest and join forms, and votes. The first two are existing doors; a vote on a form with no electorate is exactly what the voting module replaces (D4). A remainder is still possible and still reports per club at the extract.
Giving Stripe as processor under the church's own EIN and bank account (identity-verified); card, ACH and AmEx processing fees, no platform fee; donor-covered fees receipted as a gift; fund-level deductibility only; batches; statements by family with templates and mail merge, emailed as PDF; pledge campaigns; text giving to a fund keyword; anonymous gifts matched by name plus email or address, never auto-creating a profile; refunds; a QuickBooks Desktop export that omits the fund. B3's question has two shapes the record must choose between, not one: (a) the club's purposes as a caller of the Federation's one payment door, money held and remitted as the club's on the statement (D1 treatment 3 extended to gifts); or (b) a per-club merchant account under the club's own EIN, as Breeze does, which the one-door design does not contemplate. Shape (b) means the platform holds the club's processor credentials and tax status; shape (a) means every club gift passes a Federation account first. For David with the CPA (Q-3). Giving history from Breeze imports only on a yes, as the club's own.
Communications Email in bulk as BCC through a shared sending service (SPF only, no per-account DKIM; "Alternate Sending" on request); a design editor; scheduling; delivery history per recipient; Do Not Email and Do Not Text flags; unsubscribes shown as "Group Unsubscribe"; resubscribe is member-only. Texting is one-way from a shared short code (no reply; the former "Breeze" prefix was removed in 2025), 160 characters, a monthly allowance then a per-message price, US only, a consent checkbox before texting the un-enrolled and a fixed welcome text, STOP handled; statuses Enrolled, Not Enrolled, Blocked. Two-way texting is a separate product. B5's design assumed a brand registration (10DLC) on a long code; a shared short code through a provider is the other route and is what the clubs have today, with the same consent shape. The presidents' request for locally branded texts is a question for whichever route is chosen. Texting consent statuses import as consent evidence per channel: Blocked is a hard no; Enrolled is evidence for the text channel; Do Not Email/Text are hard noes (club plan §8.3).
Import, export, the API Account export covers people, tags, events, contributions and notes, not attendance; the move-in service cannot bring calendars, photos, recurring gifts, forms, follow-ups or files. The API: Api-Key header, Account Owner only, 20 requests a minute, GET-based, no webhooks documented, event listings cached up to fifteen minutes, unsupported by Breeze since February 2020; endpoints for people, tags, events, attendance (list, eligible), forms (list entries), volunteers, families, the account log and giving (list, funds, pledges — the giving endpoints confirmed from community wrappers, not the vendor page). C6's extract uses the API for people, families, tags, events, attendance, form entries, volunteer roles and (on a yes) giving, at the rate limit; the account export is the fallback for everything but attendance; forms' structures and files do not travel. The connector is built against an API its vendor no longer supports, so the parallel run is the only proof it worked.
Data policies Tithely's terms: the customer owns its content; de-identified use for industry reporting; deletion queued immediately on cancellation (a possible restore for some months, not guaranteed); financial data kept seven years; inactive accounts deleted after seven months; a thirty-day in-app restore of deletions; no published backup policy; Breeze is processor, the club is controller. A club cancels only after the archived export is verified on the drive (D66) and the cutover has run for the period the club chose (club plan §8.5). The seven-year financial retention is Tithely's, not the club's; the club's own record is the export.

What this read did not settle. Whether any real club uses the printed security codes (q5), what each club's custom fields hold (reported per club at the extract), and which clubs run votes on Breeze forms. The read opened no club's account.

What the Hub will not copy from Breeze, on purpose

  • Export to Excel, printed directories, mailing labels of members. Directory consent is a purpose; extraction is another purpose and needs its own basis. The refusal names its rule and is logged. A club that needs a mailing list mails through the platform, which keeps the withheld by name.
  • Delete a person. A record anything points at is never deleted. Death terminates it; a merge closes it with the map of what moved.
  • A leader named inside a tag's name. A group has a leader as a person on the roster, or none.
  • Notes on a person as free text everywhere. A follow-up carries one note on completion, written by the officer, visible to officers of that club, never to the member's directory and never to another club. Anything more is a case file, and the record has not decided the platform keeps one.
  • Unlimited admin users with everything. Every officer holds an exact grant at their club.

4. Rules the new objects obey

  1. A group is the club's, not the member's. Officers of that club read and write it; the member sees the names of their own groups on their own record; the directory never carries it; another club never sees it. Counts to the Federation under the suppression floor, composed like every other count.
  2. A follow-up is a task about a person, not a note about them. It carries the option, the assignee, the dates and one completion note; it is closed, never deleted; it is read by the officers of that club and by nobody else, and it is not in any directory payload or export.
  3. Nothing automatic without a named rule. A lapse raises a follow-up only if the club has switched that option on, and the follow-up names the rule that raised it.
  4. Minors are never listed where a group or a follow-up is shown outside the club's own officer screens, and never in any count that could identify one (R7).
  5. Every refusal names its rule — the wrong club, the missing seat, a minor where a minor may not be.
