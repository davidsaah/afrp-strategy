2.3 Spacing and touch

4px base scale: --s1 4 · --s2 8 · --s3 12 · --s4 16 · --s5 20 · --s6 24 · --s8 32 · --s10 40 · --s12 48

Touch target minimum is 48 px (--touch) WCAG 2.2 AA requires 24 px; Apple and Google recommend 44. AFRP's membership skews older, so 48 is the target and 44 the absolute floor. Every button, input, switch, and tappable row in this spec is at least 48.

These five rules are the substance of the fix. Everything else is styling.

3.1 Page shell and safe areas

<meta name="viewport"
      content="width=device-width, initial-scale=1, viewport-fit=cover">

/* Fixes: page titles rendering underneath the iOS status bar */
body{
  padding-top: env(safe-area-inset-top);
  padding-bottom: env(safe-area-inset-bottom);
}
.app-header{ padding-top: calc(var(--s3) + env(safe-area-inset-top)); }
.c-actionbar{ padding-bottom: calc(var(--s3) + env(safe-area-inset-bottom)); }

3.2 The overflow fix

Current behaviour A container with a fixed width (or a min-width from a desktop grid) forces inputs wider than the viewport. The member cannot see the end of their own street address while typing it. 
/* what produces the defect */
.form-container{ width: 720px; }
input{ width: 680px; font-size: 14px; }
Required behaviour Inputs are fluid and can shrink. The page can never scroll sideways. 
/* the fix — three rules */
*,*::before,*::after{ box-sizing: border-box; }
html,body{ max-width:100%; overflow-x:hidden; }

.c-input{
  width: 100%;      /* never px */
  max-width: 100%;
  min-width: 0;        /* shrink inside flex/grid */
  font-size: 16px;    /* no iOS zoom */
}
min-width:0 is the one people miss. Flex and grid items default to min-width:auto, which refuses to shrink below content size. Without it, one long email address in a row makes the whole page scroll sideways — which is exactly what the Household screen does today.

5. Household — the structural change

The only part of this spec that needs a Dynamics schema change rather than CSS. It is also the highest-value change in the document.

Current rule, quoted from the portal "Only couples and their children under the age of 18 should be added to the household. All young adults (18+) must be in their own household, even if they still live in the same physical home."

That sentence collapses three independent facts into one field. The result: a member is ejected from their family on their eighteenth birthday and a parent loses the ability to register them — while everyone still lives in the same house. In this community, parents routinely register adult children for convention.

QuestionKind of factBelongs in
Who lives together?Addresshousehold
Who may register / pay / consent for whom?Authorityhousehold_member.can_transact_for
Who does a family tier cover?Benefitmembership_coverage
Rule: age sets the default, never the rule Adding a 12-year-old grants a parent authority automatically. Adding a 20-year-old does not — but the adult can grant it. Turning 18 prompts a consent refresh, not an ejection. An adult in a household is not an error; a minor with no authorised guardian is.

5.1 Invitation flow — six steps becomes two

Current Fill details → they get an email → they claim the account → or open the red dropdown → Send Invitation → but only if never registered → email mandatory → if no email, add one via "View Details" in the same dropdown. Six steps, three conditional branches, explained in a wall of prose.
Required 1. Add member (name, DOB, relationship — email optional). 2. Optionally invite. The system decides whether that means a claim link or an account link. The member never runs the decision tree.

6.1 The regression test that matters

The overflow defect will come back the first time someone adds a desktop-width component, unless a test catches it. Run this against every portal route:

// Fails if any page can scroll sideways at iPhone SE width.
// This single assertion prevents the most damaging defect on the list.
for (const route of ROUTES) {
  await page.setViewportSize({ width: 320, height: 640 })
  await page.goto(BASE + route)
  const overflows = await page.evaluate(() =>
    document.documentElement.scrollWidth > window.innerWidth + 1)
  expect(overflows, `${route} scrolls horizontally`).toBe(false)
}
