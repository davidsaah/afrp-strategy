Why it is built this way

  • A 17-generation tree cannot be browsed as one canvas. Navigation is lineage-first: clan → branch → line, with a chart root you can move.
  • Depth control caps the render, so the chart never becomes a 30,000-node scroll trap.
  • The chart region scrolls inside its own panel. The page never scrolls sideways.

Decisions applied

  • Decision 2Provisional records from life events render immediately in amber dashes and carry a provisional flag; they are excluded from GEDCOM export and from the canonical count.
  • Decision 4Living-person detail is members-only and per-field opt-in; the default state is name plus generation.

Detail notes

  • Clan counts are live facet counts, not static copy.
  • “Spouses shown” toggles married-in people; they carry their own clan tag where one exists.
  • Print chart renders the visible depth only, with the lineage breadcrumb in the header.

Why it is built this way

  • Genealogy is an argument from evidence. Every fact panel sits beside the citations panel so a claim and its source are on screen together.
  • Change history is first-class, not an admin afterthought — contested lineages need attribution and a reversal path.
  • Two-column body keeps the record on one screen at desktop widths; it stacks below 1000 px.

Decisions applied

  • Decision 2The provisional child sits in the children list with an amber pill and an entry in the history naming who submitted it. It stays outside the canonical tree until genealogy confirms.
  • Decision 4“Directory: opted in — 4 of 9 fields” is the per-field opt-in surfacing on the tree side.

Detail notes

  • Citations use the federation's short form: Shaheen 1982, p. 214; primary vs secondary is a pill, not a footnote.
  • Tree records and member accounts are separate objects joined by an explicit link that a moderator can break.
  • All dates and IDs use tabular figures so they align down the column.

  • Facet counts update against the active filter set, so a member can see a dead end before clicking into it.

Decisions applied

  • Decision 4Members-only banner is persistent, not dismissible. Withheld fields render as “withheld” so absence is never read as an error.

Breeze parity checklist

  • People, households, groups, tags, notes, attendance history, contribution history, custom fields, archived records.
  • Saved views replace Breeze's saved filters; bulk actions cover tag, group, email, event and export.
  • Tag colours and group hierarchy were preserved through the migration so officers recognise their own data.

Decisions applied

  • Decision 3This is the module that had to be deeper than Breeze, not equal to it — because dues, national membership tier and club membership are now one record rather than two systems.
  • Decision 1Family · free yr 1 appears as a dues state, so an officer never mistakes the couple for unpaid.

Detail notes

  • Contact column shows reachable channels, which is what messaging consumes. No SMS consent is a tag, so it is filterable and countable.
  • The table scrolls inside its own wrapper with a sticky header row; the page itself never scrolls sideways.
  • Archived people are excluded by default but remain searchable — Breeze's behaviour, kept deliberately.

Why it is built this way

  • Integrations fail quietly. Every panel leads with a health pill, a last-run timestamp and an error count, so a silent failure is visible on the first screen an administrator opens.
  • Auto-publishing is a table of rules with an approval column, not a set of toggles — who authorised the post matters more than whether the switch is on.
  • The tracker is a live table, not a status slide. Owners are named club officers; unassigned clubs are visibly unassigned.

Decisions applied

  • Decision 3The Breeze replacement is run as a tracked programme: 12 migrated, 6 dual-running, 8 still on Breeze, with a hard end date at the contract expiry.
  • Decision 4Directory and family-tree data are excluded from every outbound channel — stated on the publishing panel, enforced in the rules engine.

Detail notes

  • Obituaries never auto-publish. Deliberate.
  • Mailchimp unsubscribes write back to the member record so a club officer cannot undo a member's opt-out.
  • Authorize.Net declines escalate to a club officer task after two automated dunning attempts.
